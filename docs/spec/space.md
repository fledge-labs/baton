# Baton Space 行为规格

状态：`SPEC_GRAPH_READY`。本版冻结已核实的产品语义和 Baton 存储/API 不变量，含命名派单、依赖图、施工面清单（x_ready）及 scope 路径前缀冲突判定，供实现与独立验收使用；不代表实现已通过，也不代表 ChatGPT Space 界面等价性已验收。核验日期：2026-10-17。

**Owner 决定（已执行）：移除内置 Codex worker。** Baton 是通信与协作层，不执行任务；执行属于通过 MCP、HTTP、A2A 或适配器连接的外部 agent。因此下文凡与自动 worker 相关的条目（自动派发、`claim_next`、`worker_success` gate、`fail_auto`/`finish_auto`/`interrupt_auto`、dispatcher 服务主体、worker 健康与失败分类）一律标为“按 owner 决定移除”，编号保留、不再存在对应实现。`execution_mode='codex'`、`gate_mode='worker_success'` 以及 `a2a_id`、`backend`、`dispatch_started_at` 列是**历史值**：旧行仍可读取，schema 的检查约束继续允许它们以便旧数据库迁移，但没有任何路径写入、领取或批准这些行。不带接收人的 `submit_task` 现在创建手工、未指派的任务（见 X12）。

**Owner 决定（2026-10-17）：产品范围收窄为通信与任务协作。** “Baton 不做文档协作，就做通信与任务协作平台。”页面（page）在产品上呈现为 channel（频道）：消息、评论与任务的容器，API 名称（`create_page`/`get_page`/`list_pages`）不变。下文 O2 中关于页面块、以及块编辑、提案与署名历史（`create_block`、`update_block`、`revert_block`、`proposal_*`、`list_attribution`、`comment.selection`）的条目描述的是已有实现，现已标为弃用，只做标记、行为不变；`kind='task'` 的块通过 `get_block`/`list_blocks` 永久受支持。弃用清单、替代和响应标记见 [API 的 Deprecated 一节](../api.md#deprecated)。

范围：替换 Agent Mail 为 Baton 自有的空间、页面、评论、提及、任务与协作协议。采用 PostgreSQL，优先实现数据库与 HTTP 行为；不连接真实 ChatGPT 空间，不做同步、导入既有账户或协议互操作。

## 已核实的官方行为

**O1 · 官方 · 空间与页面。** Space 汇集可访问的页面、文件和共享工作；一个 space 可按主题或团队组织页面。页面可以独立存在，也可有子页面。Baton 的同名实体必须保留这一区别，不把 workspace、space、page 合并为一个权限对象。[S1](https://learn.chatgpt.com/docs/space/)、[S5](https://learn.chatgpt.com/docs/space/getting-started#group-related-pages-in-a-space)。

**O2 · 官方 · 页面块。** 页面由块组织。文档明确列出标题、段落、列表、清单、表格、代码、强调、图片、文件、子页面/页面链接、文件/页面/聊天引用、可视化、Prompt、Task、Agent Instructions。块名称不是公开 JSON schema；Baton 的类型名、字段、顺序编码和执行方式均另标 x_扩展。不能把一个任务块的存在等同于某任务已经被调度。[S2](https://learn.chatgpt.com/docs/space/pages#add-content-with-the-insert-menu)、[S4](https://learn.chatgpt.com/docs/space/agents#verify-recurring-work-separately)。

**O3 · 官方 · 访问级别。** view 用于阅读，comment 用于阅读并反馈，edit 用于修改内容。修改他人的访问权限还需要管理分享的权限，不能仅凭“可编辑内容”推断“可分享”。可用接收者及分享方式受账户、workspace 和接收者类型影响；Team 邀请可能仅有 view/edit，不提供 comment。[S3](https://learn.chatgpt.com/docs/space/collaboration#choose-an-access-level)、[S6](https://learn.chatgpt.com/docs/whats-new/devday-2026#chatgpt-space)。

**O4 · 官方 · 继承与移除。** 共享 Space 的访问权适用于其页面；页面分享也赋予对子页面的访问权。直接授权和继承授权应可区分。移除页面的直接邀请，不能撤销仍来自父页面或 Space 的继承权；需要在相应来源修改授权。[S3](https://learn.chatgpt.com/docs/space/collaboration#understand-inherited-access)。

**O5 · 官方 · 评论与提及。** 可在页面选定文本后评论，或用评论讨论问题、请求修改。对人的评论/提及是给对方的反馈；在页面内或评论中以 `@ChatGPT`/`@dot` 加请求，是请该 agent 行动。原文要求检查接收者并审阅回复及页面改动，不支持“每个 @ 字符都必然执行任务”的推断。[S2](https://learn.chatgpt.com/docs/space/pages#work-with-selected-text)、[S4](https://learn.chatgpt.com/docs/space/agents#choose-how-to-ask-for-help)。

**O6 · 官方 · 提案与审阅。** 选区的 Ask for change 在可用时用于请求修订，应先审阅提议的修改再接受。Generate 文本可接受、继续要求修改或撤销。原文没有定义这几个动作的事务顺序、冲突处理或撤销范围。[S4](https://learn.chatgpt.com/docs/space/agents#revise-a-launch-brief)、[S2](https://learn.chatgpt.com/docs/space/pages#draft-content-with-generate)。

**O7 · 官方 · 贡献归属。** 页面在功能可用时提供 Show attribution，用于查看贡献者。原文没有保证逐字符、逐块、逐操作或永久历史的具体粒度。Baton 的归属字段及审计记录不得冒充该未公开数据模型。[S2](https://learn.chatgpt.com/docs/space/pages#comment-and-collaborate)。

**O8 · 官方 · Agent 与权限背景。** Space 中可用的 agent、连接工具和控件取决于访问条件；不同协作者可以有不同 agent、工具及指令。DevDay 回顾另说明 workspace connections 使用被连接账户的权限，但这不直接给出 Space 每个评论请求的授权算法。Baton 必须显式定义自己的主体和委托边界。[S4](https://learn.chatgpt.com/docs/space/agents)、[S6](https://learn.chatgpt.com/docs/whats-new/devday-2026#workspace-connections)。

**O9 · 官方 · 来源内容权限。** 链接的源文件保留自身权限；复制或总结到页面的内容则对页面读者可见。分享页面不自动分享私人聊天或已保存记忆。Baton 不因页面可读而声称外部引用也可读。[S1](https://learn.chatgpt.com/docs/space/#connect-your-sources)、[S3](https://learn.chatgpt.com/docs/space/collaboration#review-together)。

## Baton API 与存储契约

以下规则全部是 **x_扩展**。官方链接只标明所对应的产品背景，不是这些实现细节的来源或 OpenAI API 声明。

**X1 · x_protocol。** HTTP 统一采用 `POST /v1/space/{operation}`，协议标识为 `x_protocol: "baton.space.v1"`。URL 不必逐段含 `x_`，但文档、响应和客户端不得把它称作官方 Space API。操作名及方法参数由同期实现 contract 明列允许列表；禁止按输入反射调用任意存储方法。未实现操作必须明确拒绝，不能伪装成成功。[官方背景：S1](https://learn.chatgpt.com/docs/space/)。

**X2 · 主体与授权。** 认证层确定 `principal`，区分 human、agent；principal kind/account 仅由 token 管理员指定，API 请求不能修改它们或覆盖真实 actor。内容写入、评论、分享、任务提交、领取及审阅必须在服务端重新检查当前有效权限。服务主体 `baton-service` 没有客户端凭据，只用于 webhook 投递、响应时限升级和 schema 检查，不能借此获得页面编辑、分享或审批权；旧版自动任务的窄服务接口和 `codex-worker` 主体**按 owner 决定移除**（名称作为历史行中的服务主体保留，不可签发）。`requested_by` 与 `performed_by` 必须分别保留，服务执行不能冒充用户署名。[官方背景：S3](https://learn.chatgpt.com/docs/space/collaboration#choose-an-access-level)、[S4](https://learn.chatgpt.com/docs/space/agents#work-with-others)。

**X3 · 授权存储。** 直接授权记录资源、接收主体及 view/comment/edit；继承权由 Space/父页面的当前有效授权计算，不能复制成不会失效的直接邀请。Baton 自定义有效权限为可用授权的最高级别，`view < comment < edit`；这是自身的冲突规则，不是官方已公开算法。页面管理分享的 owner 取所属 Space 的 owner，页面创建者只记归属，不因创建行为获得隐式独立 owner 权；临时 edit 被撤销后不能凭创建者身份保留访问或分享权。分享管理权限仍与内容 edit 分开检查。Baton 首版 Team 仅支持 view/edit，comment 授权给人；未知接收者类型拒绝或明确声明不支持。这个首版角色矩阵是 x_选择，不是所有官方账户的普遍矩阵。[官方背景：S3](https://learn.chatgpt.com/docs/space/collaboration#understand-inherited-access)。

**X4 · 页面、块与归属。** PostgreSQL 保存稳定的 Space、Page、Block 标识和父子关系；拒绝循环父子关系。Baton 存储中所有页面归属一个 Space，独立页面可用私有 home Space 表示；这是内部存储选择，不能据此声称官方页面必须先属于一个 space。页面内容版本单调递增，归属至少保留实际 actor、提交版本和数据库时间。块 payload、顺序表示、版本比较及历史保留是 Baton 自有格式。内容变更必须携带实现 contract 定义的基线版本；陈旧基线返回冲突，不静默覆盖。首版不声称 CRDT、实时协同光标或自动合并与 Space 一致。[官方背景：S1](https://learn.chatgpt.com/docs/space/)、[S2](https://learn.chatgpt.com/docs/space/pages#rearrange-blocks)、[S2 归属](https://learn.chatgpt.com/docs/space/pages#comment-and-collaborate)。

**X5 · 评论、提及与 inbox。** 评论线程绑定页面或任务；任务与其报告线程使用同一个 UUID。对 person 和 agent 的提及都保存显式目标 principal，而不是把显示名称或共享 account 当成该接收身份。任务上下文中的 `@agent` 请求产生发给目标的 inbox `action_request`，保留 `requested_by`、接收者、上下文及 task ID；普通反馈与行动请求区分。提及不直接设置 holder，不暗改 assignee 或授予权限，exclusive claim 以 X12 的显式派单为准。`fetch_inbox` 是 Baton 自有的 mentions + assignments 查询，不是官方 Inbox API：mentions 按记录的显式接收主体匹配，assignments 只把 `assignee_principal` 等于当前 principal 的任务作为其派单。访问检查仍使用该主体所属账户的当前有效权限；共享 account 不会让另一 principal 自动成为收件人或可领取者。结果应包含关联 task ID、当前状态、`assignee_principal` 及当前是否可领取的提示，失权后不得泄漏任务；可领取提示不是保留席位，实际 claim 仍须重新验证权限、租约、fence、scope 与 X17 的依赖 gate。接收者自愿 poll/claim/report，通知不会向其主机推送进程、修改配置或选择工具权限。[官方背景：S4](https://learn.chatgpt.com/docs/space/agents#choose-how-to-ask-for-help)。

**X6 · 幂等与事务。** 普通 mutation 使用稳定 UUID `operation_id`；同一效果的重试复用它。PostgreSQL 在同一事务内按 actor + operation_id 记录规范化请求摘要、业务变更及可重放结果；同键同请求不再产生效果，同键异请求返回 `409`。`submit_task` 另保留现有稳定业务 `idempotency_key`，同 actor + key 不创建第二任务，不能用每次随机生成 operation_id 绕过提交去重。幂等请求摘要包含操作及所有影响效果的字段，不记录秘密原值。重放仍重新检查当前读/操作权限，失权后不得泄漏旧结果。[官方背景仅为产品协作：S3](https://learn.chatgpt.com/docs/space/collaboration#review-together)。

**X7 · HTTP 结果。** 未认证返回 `401`；对象对调用者可见、但权限不足以执行该操作返回 `403`；调用者对已存在对象没有 view 权限时，与对象不存在一样返回 `404 not_found`，响应不泄漏存在性（`get_task`、`list_comments`、`get_page`、评论、块与任务写入等一律如此；对他人目标——指定接收人、交接对象——的缺权检查仍是 `403`，因为调用者看得见对象）。陈旧版本、键复用冲突、作用域冲突或陈旧 fence 返回 `409`，无效参数返回 `422`。错误只含稳定错误码与安全说明；`422 invalid` 可附带 `error.details`（见 X22）；不暴露凭据、内部 SQL、其他主体的不可见任务详情。写事务失败必须整体回滚，不留下半条评论、幂等记录或成功审计事件。[官方背景：S3](https://learn.chatgpt.com/docs/space/collaboration#resolve-an-access-problem)。

## x_claim、x_scope 与 x_handoff

**X8 · x_claim 租约与 fencing。** 一个任务同一时刻只有一个有效持有人。`assignee_principal` 是派单对象，holder 是当前有效 claim 的持有人；派单本身不创建租约或占用 scope。有效性由 PostgreSQL 的当前时间判断，不能信任客户端时钟；事务等待锁之后必须使用新的数据库时间判断期限。`lease_expires_at <= database_now` 即失效。每次新取得或交接所有权都提高该任务单调 fence；续租不降低或重置 fence。持有人、有效租约、当前 fence 三项必须同时匹配，才能续租、提交结果或交接。已过期或旧 fence 的请求拒绝，即使原持有人稍后恢复。续租重放不会再次延长期限。过期释放独占权无需依赖及时运行的清理任务，但不能清空 assignee；命名任务仍只有该指定 principal 在重新通过权限与状态检查后可领取。[官方背景仅为协作：S4](https://learn.chatgpt.com/docs/space/agents#work-with-others)。

**X9 · x_scope 锁域。** 第一版所有 Space 强制使用 `global` repository namespace；`create_space` 不提供可变 namespace，若实现保留 `scope_repository` 字段则只接受 `global`。排斥范围是同一 Baton 实例或共用 PostgreSQL 权威内的跨 Space 领取，不能声称独立数据库之间有分布式互斥。新 namespace 仅能通过未来管理员契约扩展，不能由请求自由指定以绕过冲突。领取事务须串行化该 namespace 的“查重叠 → 占用”步骤，防止并发检查同时为空。[官方背景仅为分工：S4](https://learn.chatgpt.com/docs/space/agents#work-with-others)。

**X10 · x_scope 规范化与路径前缀冲突域。** 声明路径仍采用仓库相对路径及 `/` 分隔符，去除重复分隔符、结尾 `/` 与 `.` 段，拒绝绝对路径、驱动器前缀及 `..` 越界段；空/根范围规范化为仓库根。路径保留声明时的大小写，供展示与审计。**path 重叠规则。** 两个 path 声明重叠，当且仅当规范化后二者相等，或其中一个是另一个在 `/` 边界上的目录前缀：`docs/design` 与 `docs/design/roadmap.md`、`docs` 重叠，与 `docs/designer`、`src` 不重叠；`src/a` 与 `docs/b`、`src/a` 与 `src/ab` 不重叠，可同时领取。空路径（仓库根占位范围）与任何 path 重叠。默认按大小写敏感比较；运营者可设置环境变量 `BATON_SCOPE_CASE_INSENSITIVE=1`（默认关闭，仅值 `1` 生效）改为大小写不敏感比较，用于大小写不敏感的文件系统。**已知限制（A17）。** Baton 只比较声明文本，不解析符号链接、硬链接或其他别名，也没有可信文件拓扑 authority：通过不同路径指向同一批文件的声明（例如 `current` 是指向 `releases/42` 的符号链接时的 `current/app.py` 与 `releases/42/app.py`，或大小写不敏感文件系统上未开启该选项时的 `Src` 与 `src`）**不会**被检测为重叠。声明者须自行用真实、规范的路径声明；客户端映射不能缩小实际锁域，也不能依赖 Baton 发现别名冲突。claim 与 ready 使用同一规则（`claim_next` 按 owner 决定移除）；已有的 claim 不受影响，也不会被改写。path 与 migration 是两个独立的声明域；migration 只按完整标识精确相等互斥，相异 migration 可并行，path 声明不自动保护 migration。module 声明采用覆盖全部声明域的 whole-repository 范围，与 path、module 及任意 migration 均冲突，不接受客户端模块映射来绕过；migration 保持完整标识精确相等语义；`none` 永不重叠。任务需同时保护文件和 migration 时应同时声明两者。**显式 `none`。** scope 种类 `none`（`{"kind":"none"}`，没有 `value`）表示该任务不触碰任何仓库路径、模块或 migration：它不占用任何锁域，与任何 claim（包括 path、module、migration 和另一个 `none`）都不冲突，因此多个无文件足迹的审阅、文档或试用任务可以同时被领取。`none` 不能与其他 scope 条目组合（含仓库根占位范围），否则请求无效；重复的 `none` 合并为一个。省略 `scopes` 时，所有任务（`create_task_block` 和不论是否带 assignee 的 `submit_task`）默认为 `[{"kind":"none"}]`；旧版自动 codex 任务的仓库根占位范围 `[{"kind":"path","value":""}]` 是历史值。显式传空列表保持旧行为，一律存储仓库根占位范围。已存在的任务行不会被改写。已持久化请求的幂等摘要保持有效：省略 `scopes` 的请求在计算摘要时仍按旧的仓库根占位范围处理，与引入 `none` 之前相同。未来如需别名感知的锁域，须另行建立可信拓扑/别名映射和验收，不能把声明路径当成已有 authority。对外冲突信息仍受 X2 权限限制。[官方背景仅为分工：S4](https://learn.chatgpt.com/docs/space/agents#work-with-others)。

**X11 · x_handoff。** 交接必须在同一事务内校验原持有人、未过期租约、旧 fence 和接收者的现有 edit 权限等资格，然后保留任务的 base commit、上下文、证据引用和线程，将 holder 与 `assignee_principal` 一起切换为接收 principal 并提升 fence；不会自动授予接收者访问权限。base commit 在交接中不可变，包括原值为 `None/null` 时也不得借交接填入新值；context/evidence 仅追加，不覆盖、删除或因空缺字段清空旧材料。作用域不得在交接时无检查地扩大，扩大必须重新检查重叠。原持有人在提交后不能继续使用旧 fence 写入。失败交接不改变所有权、assignee 或材料，幂等重放不得重复追加上下文或证据；普通 assignment 不能代替有效 claim 的交接检查。[官方背景仅为协作上下文：S3](https://learn.chatgpt.com/docs/space/collaboration#review-together)。

## x_gate、任务兼容层与 x_audit

**X12 · 状态、x_assignment 与执行模式。** Baton canonical task state 为 `queued / claimed / awaiting_gate / done / failed / interrupted`。正常路径为 queued → claimed → awaiting_gate → done；failed 与 interrupted 现在只出现在旧版 worker 留下的行上（执行失败与执行结果不确定），当前代码不再写入。手工候选结果被 gate 拒绝后返回 queued，之后新领取取得新的 epoch。lease 过期释放领取权，不能依赖旧行的 claimed 文本继续阻塞或授予写权。旧 MCP `get_task` 兼容视图将 claimed 映射为 working、done 映射为 completed；兼容映射不能隐藏 failed/interrupted，也不能把 awaiting_gate 提前映射为 completed。任务线程 UUID 保持不变。命名派单全部是 Baton x_扩展，外部字段名为 `assignee_principal`，内部 `assigneeActor` 不构成另一种身份或 OpenAI 格式。调用者先通过任务操作授权检查；显式 `assign_task` 或带 `assignee_principal` 的 `submit_task` 只能指向已具该任务有效 edit 权限的 principal，不自动增加 grant。设置 assignee 后，只有该确切 principal 可以 claim；同 account 下其他 principal 即使有 edit 也不得替领。**`submit_task` 总是创建手工任务，Baton 不派发到任何地方（自动 Codex worker 路径按 owner 决定移除）。** 不带 assignee 时任务**未指派**（`assignee` 为 null，没有响应时限）、范围省略时为 `none`、reviewer 默认为请求者；没有 `role` 时，任何对其页面有 edit 权限的主体都能在 `ready` 里看到并 `claim` 它。带 `role` 且未指派时，只有当前在该任务所在 Space 持有该角色的主体能在 `ready` 和 `ready_for_role` 里看到并 `claim`（X27）。把带 `role` 的任务指派给不持有该角色的主体，只有 Space 根或持有覆盖该 Space 的审批人委托的主体可以，授权记在 `role_assign_authority`；任何主体都不能把角色任务指派给自己，除非自己持有该角色，不论当前 assignee。非持有人 `claim` 仅当自己就是该接收人且 `role_assign_authority` 有值。没有 edit 权限的主体看不到它（404）；默认页面是请求者私有的，要让别人领取须使用共享页面。带 assignee 时使用手动 pull 模式，只有该 principal 能领取（指定给调用者的角色任务，非持有人还须有上述授权）。两种情况下任务都只由接收 agent 自愿 poll inbox、claim、执行并在同一线程 report。`submit_task` 与 `create_task_block` 增加了可选参数 `role`；其余既有参数不变。不会安装 agent、推送任务进程、访问其主机或替它放宽工具权限。[官方背景仅为任务请求：S2](https://learn.chatgpt.com/docs/space/pages#add-content-with-the-insert-menu)、[S4](https://learn.chatgpt.com/docs/space/agents#choose-how-to-ask-for-help)。

**X13 · x_gate。** 手工 `submit_result` 必须持有 live lease，在同一事务中冻结候选结果的 `result_epoch`（对应当次 claim 的 epoch/fence）、`result_author` 的确切 principal、基线与证据，释放 claim/scopes 并进入 awaiting_gate；之后审阅不依赖仍在续租的 claim。gate 请求携带固定 `expected_epoch`，必须匹配当前待审候选。reviewers 配置保存 principal IDs，不是 account IDs；Space owner（根）可直接批准；其他主体须是配置的 reviewer principal、仍通过其 account 的有效权限检查，并且持有覆盖该任务的有效审批人委托（X25），人类与 agent 一视同仁。自批判定见 X25：除根（需显式 `self_approval`）外，结果作者以及在被审批 epoch 持有过 claim 的任何 principal 或 account 都不能批准，不能用租约已释放或当前 holder 改变绕过；只创建请求的任务 owner 可以批准。任务可要求两个不同审批人对同一 `result_epoch` 都通过才 done（X25 双人确认）。客户端不能直接把 canonical state 写成 done。`submit_task` 默认 reviewer 为 requestor principal，并拒绝 requestor principal 等于 assignee principal 的请求；需要派给自己时应使用 `create_task_block` 显式配置另一 principal 作为 reviewer。批准后才 done；拒绝后回到 queued，旧候选及决定作为历史保留，下次 claim 使用新 epoch，旧批准不能完成新一代任务。`worker_success` 自动 gate 及其服务写入路径**按 owner 决定移除**；历史 `worker_success` 行只读，没有任何路径可以 gate 它们。[官方审阅背景：S4](https://learn.chatgpt.com/docs/space/agents#revise-a-launch-brief)。

**X14 · 提案审阅。** 页面修改提案与任务 gate 是不同对象。Baton 可以保存拟议修改、目标版本、发起者及审阅决定；接受时重新检查权限和目标版本，在同一事务中应用修改并记录决定。拒绝或继续修订不得被记录成接受。Baton 的原子接受和版本冲突策略属于 x_扩展；Space 的精确 undo 行为仍待界面实测，不用自身实现冒充已对齐。[官方背景：S2](https://learn.chatgpt.com/docs/space/pages#draft-content-with-generate)、[S4](https://learn.chatgpt.com/docs/space/agents#revise-a-launch-brief)。

**X15 · 读取视图。** `list_tasks` 默认只列当前 principal 自己的任务，不默认枚举整个共享 Space；`get_task` 在当前有效 view 权限允许时可读取共享任务；`fetch_inbox` 按 X5 的当前接收主体返回 mentions 与 assignments。这三种不同可见性都是 Baton 自有 API 规则，不从官方 Space 的 sidebar 或 sharing 菜单臆造查询协议。[官方背景：S3](https://learn.chatgpt.com/docs/space/collaboration#choose-an-access-level)。

**X16 · x_audit 不可变追加。** 业务事件在产生业务效果的同一 PostgreSQL 事务中追加，至少关联真实 actor、operation/task/thread 标识、数据库时间、结果状态和必要的 fence/版本；命名任务的 assign → claim → result → gate 必须能按同一 task ID 关联，并区分 requestor、assignee、result_author 与 reviewer 的 principal。幂等重放不能再追加一条代表同一效果的新事件。应用数据库角色不得 UPDATE/DELETE 审计行，迁移所有者与应用权限分离。凭据、完整 prompt/评论正文及证据秘密不进入审计，仅保存必要元数据和引用。该约束不声称能抵抗数据库超级用户或宿主失陷；也不是官方 attribution 的存储形式。[官方背景仅为归属：S2](https://learn.chatgpt.com/docs/space/pages#comment-and-collaborate)。

**X17 · x_graph 依赖图、plan 与 ready。** 任务通过 `depends_on` 组成有向无环图；`A.depends_on=[B]` 表示 A 等待 B 通过 gate。任务依赖、图事务、ready 与进度推导全部是 Baton 自有 x_协议，官方 Task 块说明不定义这些行为。图由人或外部 planning agent 创建；Baton 只存储、校验和执行约束，不内置 planner，不从任务正文自动推导依赖。[官方背景仅为任务块：S2](https://learn.chatgpt.com/docs/space/pages#add-content-with-the-insert-menu)。

- **依赖可变性。** 追加依赖要求调用者当前可 edit 被修改任务，并且任务当前为尚无 execution 的 queued。claimed、awaiting_gate、done、failed、interrupted 均拒绝；lease 过期本身不能让仍处于 claimed 的任务绕过此检查。只有其他合法恢复流程已将其恢复为 queued，且仍无 execution，才满足可变性条件；plan 不负责回收或重置任务。曾经执行后重新 queued 的任务也不满足“尚无 execution”。执行已启动、已有持久执行记录或执行状态不确定时不得追加；没有结果不能单独证明没有执行。依赖追加不能重置现有结果、gate、assignee 或 fence 来伪造未执行任务。现阶段只规定追加，不开放删除依赖以绕过等待。[官方背景仅为协作审阅：S4](https://learn.chatgpt.com/docs/space/agents#work-with-others)。
- **依赖权限。** 每个被引用的 dependency 都必须对调用者当前可见且至少具 view 权限；知道 task ID 不产生查看依赖状态的权利。plan、ready 及领取时均重新检查，不因建图时曾有访问权而永久放行。隐藏或失权 dependency 的错误、就绪说明及进度不能泄漏其状态、内容或身份；不通过自动授权来补齐权限。[官方背景仅为访问控制：S3](https://learn.chatgpt.com/docs/space/collaboration#choose-an-access-level)。
- **节点创建与初始依赖。** 新任务先通过 `create_task_block` 或 `submit_task` 创建；这两个创建 API 均支持可选 `depends_on`，引用已存在任务的 UUID。节点和其初始依赖边必须在同一事务中完成权限、引用及 DAG 校验后提交，任一失败则新任务与依赖边整体不生效。有依赖的任务（包括不带接收人的 `submit_task`）应采用此原子创建方式，不能先发布无依赖任务、再调用 plan 补依赖而让别的主体抢先领取。创建时已有未通过 gate 的 dependency，任务即使已入队也不能领取；默认命名派单与 gate 规则不变。[官方背景仅为任务块：S2](https://learn.chatgpt.com/docs/space/pages#add-content-with-the-insert-menu)。
- **plan 原子性。** Baton 合同为 `plan(operation_id, graph:[{task_id:UUID, depends_on:[UUID,...]}])`。它使用 X6 的稳定 operation_id，原子建立或扩展既有任务之间的依赖图；不创建新任务实体，也不接受请求内的符号节点键。graph 中每个 task_id 及 depends_on 项都必须引用已存在的任务 UUID。无效/不存在的 UUID、自依赖、循环、越权引用或任一待修改任务不满足可变性时，整个事务回滚，包括本次依赖边、幂等效果和成功审计，已有任务不被删除或重建。同 operation_id 同请求重放不再次追加边，异载荷复用冲突。并发 plan 必须在共同 PostgreSQL 权威内维护 DAG，不能让两次各自通过的检查合成环；与 claim 并发时也必须重验可变性，不能向已经开始的任务补塞前置条件。这是建立或扩展图的存储操作，不是内置拆图 planner，也不是官方 wire schema。[官方背景仅为共享工作：S3](https://learn.chatgpt.com/docs/space/collaboration#review-together)。
- **依赖满足。** 每次 `claim` 都必须在取得持有权前原子校验全部 dependency：canonical state 为 done，且存在对应其当前 epoch/result_epoch 的有效 gate pass。仅有历史 pass、旧 epoch 的批准、状态文本 done 而缺少当前 gate 证明，或者 awaiting_gate，均不满足。无依赖任务只跳过这一条件，其他权限、派单、租约、scope 与 fencing 检查不变。（`claim_next` 与自动 worker 路径按 owner 决定移除。）[官方背景仅为审阅：S4](https://learn.chatgpt.com/docs/space/agents#revise-a-launch-brief)。
- **ready 查询。** Baton 合同为 `ready(page_id=None, limit=50)`：page_id 可选，用于限定页面，默认最多返回 50 条；指定页面或提高 limit 不改变权限与可领取检查。它仅返回调用者当前可 edit、assignee 允许该确切 principal 领取、状态与租约允许领取、依赖全部满足且按 X10 当前无 scope 冲突的任务。依赖及任务可见性不足时不返回泄漏性条目；不把同 account 的其他 assignee 当成当前 principal。ready 和 inbox 的可领取提示只是当前快照，不预留 claim；实际 claim 必须在原子事务中重验全部条件，两个调用者看到同一候选不意味着都能获得它。[官方背景仅为访问与分工：S3](https://learn.chatgpt.com/docs/space/collaboration#choose-an-access-level)、[S4](https://learn.chatgpt.com/docs/space/agents#work-with-others)。
- **进度。** 图进度从有权读取的任务 canonical state 及其当前 gate 结果派生，不维护可独立写入、与任务真相分叉的第二份 tracker。状态、结果与 x_audit 仍遵循既有事务及身份规则；依赖图不改变命名 agent 自愿 pull、原线程报告、reviewer 审阅和真实原生验收边界。[官方背景仅为审阅与归属：S4](https://learn.chatgpt.com/docs/space/agents#revise-a-launch-brief)、[S2](https://learn.chatgpt.com/docs/space/pages#comment-and-collaborate)。

## x_ready 施工面清单

**X18 · x_ready 施工面清单与领取门控。** 任务可携带一份施工面清单，并可要求在清单完整前不得领取；这是 Baton 自有 x_协议，官方 Task 块说明不定义这些行为。**x_ready 不是 X17 的 `ready` 查询**：`ready(page_id=None, limit=50)` 只列出调用者当前可领取的任务，不改变任务；x_ready 是任务上的清单数据加领取门控，决定任务是否具备被领取的前提。`ready` 查询保持原样，只是额外不返回清单不完整的任务。[官方背景仅为任务块：S2](https://learn.chatgpt.com/docs/space/pages#add-content-with-the-insert-menu)。

- **数据。** `work_face` 可为空，格式严格为 `{"environment":[str],"fixtures":[str],"constraints":[str],"migration":str|null,"acceptance_command":str}`：五个键都必须出现，不允许多余的键；三个列表各最多 20 项，每项去掉首尾空白后非空且不超过 500 字符；`acceptance_command` 去掉首尾空白后非空且不超过 2000 字符；`migration` 为 null 或非空且不超过 200 字符的字符串。校验失败返回 `invalid`（HTTP 422）。存储保留去除首尾空白后的规范形式。`require_work_face` 默认 false，`task_kind` 为 `construction`（默认）或 `prep`；已有任务按默认值处理，行为不变。
- **完整性。** 仅当 `require_work_face=true` 时，下列三项必须同时满足才算 work face 完整：`base_commit` 非空；`scopes` 有声明（仓库根占位范围和显式 `none` 都不算声明仓库范围，因此至少要声明一个具体 scope；`none` 任务因而在 `work_face_missing` 中仍列出 `scopes`）；`work_face` 非空且格式合法。task view 增加 `work_face`、`require_work_face`、`task_kind` 以及 `work_face_missing`（缺失项名称列表，取值只能是 `base_commit`、`scopes`、`work_face`；不要求清单的任务恒为空列表）。
- **领取门控。** `claim` 的领取步骤在现有依赖与 scope 检查之外，要求 `require_work_face` 为真的任务清单完整，否则返回 `work_face_incomplete`（HTTP 409）；`claim` 的重放路径同样检查。`ready` 不返回清单不完整的任务。（`claim_next` 的跳过逻辑按 owner 决定移除。）
- **准备任务。** 准备任务门控完全复用 X17：施工任务 `depends_on` 一个 `task_kind='prep'` 的任务，该准备任务 done 且当前 epoch 有 gate pass 之前，施工任务按既有规则返回 `dependency_blocked`。不另设一套依赖逻辑。
- **set_work_face。** `set_work_face(operation_id, task_id, work_face, base_commit=None)` 只允许目标任务为 queued、epoch 为 0 且无执行记录（规则与 plan 相同），否则返回 `stale_claim`（409）。调用者必须对任务所在页面有当前 edit 权限，并且是任务 owner、或在 reviewers 中（按 principal 精确匹配）、或当前持有有效租约，该租约对应的任务 `task_kind='prep'` 且目标任务 `depends_on` 它；否则返回 `forbidden`。`base_commit` 只能在当前为 null 时设置一次，重复传原值是 no-op，传别的值返回 `operation_conflict`。它使用 X6 的 `operation_id` 幂等（重放重新检查权限），审计事件为 `task.work_face_set`，元数据只含键名列表与 work_face 规范 JSON 的 sha256，不含正文。`create_task_block` 与 `submit_task` 也可在创建时给出 `work_face`、`require_work_face`、`task_kind`，三者计入幂等请求摘要。
- **不执行。** Baton 绝不执行 `acceptance_command`；它只是给领取人与 gate 审阅人阅读的信息，通过与否仍由 X13 的 gate 决定。

## 通知与异步送达

**X19 · 通知 outbox、wait_inbox 与 webhook。** 通知是 Baton 自有 x_扩展，不代表 Space 的通知渠道（U2 仍待界面实测）。`baton.x_notify` 行与触发它的业务效果、审计在同一 PostgreSQL 事务写入：mention、任务指派（submit_task/assign_task/create_task_block）、任务线程中的评论（发给 owner、assignee、持有人、reviewers，不含作者）、进入 awaiting_gate（发给 reviewers）、gate 决定（发给 owner、assignee、持有人）和 handoff（发给新持有人）；`task.failed`（旧版 worker 的确定性失败，`fail_auto`）**按 owner 决定移除**，事件名为兼容旧订阅与旧 outbox 行保留，当前没有路径产生它。收件人在插入时必须有页面 view 权限，读取与投递时重新检查；outbox 行和默认 webhook 负载只含 id、seq、event、object_type、object_id、thread_id、created_at、recipient（以及 outbox 内的触发者标识），审计与日志不得包含 prompt、评论正文或结果文本；`wait_inbox` 行和选择 `include_preview` 的 webhook 另带读取时现算的预览（X21）。`wait_inbox(after_seq, timeout_seconds ≤ 55, limit)` 在有可见行时立即返回，否则有界等待，不忙等，并发有上限。`webhook_subscribe/list/delete` 只处理调用者自己的订阅和通知：签名密钥由服务端生成并只返回一次，投递带 HMAC-SHA256 签名，至少一次、指数退避最多 8 次后 dead-letter，终局结果审计；URL 必须通过 https 与 SSRF 检查（连接时复核，不跟随重定向），每个 principal 最多 10 个订阅。通知只提示事项，不启动执行，命名 agent 仍自愿 pull。

**X20 · 响应时效约定与超时升级。** 响应时效是 Baton 自有 x_扩展，对应设计简报“沟通原则 3：每个优先级有响应时限，超时升级给负责人或改派”；官方 Space 文档不定义任务时限、升级或改派（U2 通知时机仍待界面实测）。任务新增 `priority`（`urgent`/`normal`/`low`，默认 `normal`）、`respond_by`、`responded_at`、`escalated_at`、`escalate_to`（principal，默认任务 owner）和可选的 `fallback_assignee`（principal）。时限只适用于有 assignee 的手工路径任务，时钟在 assignee 被设置时启动：`submit_task`/`create_task_block` 带 assignee，或 `assign_task`/`handoff` 改为新的 assignee（重置 `respond_by`、`responded_at`、`escalated_at`）；同一 assignee 重复指派不重置。所有时间取数据库时钟；各优先级的分钟数是 bridge 配置，默认 `urgent=20,normal=60,low=1440`，可由环境变量 `BATON_RESPONSE_MINUTES="urgent=20,normal=60,low=1440"` 覆盖（可只写部分优先级，格式非法则 bridge 启动失败）。“已响应”指 assignee 领取任务，或 assignee/当前持有人在该任务线程发表评论，`responded_at` 只在首次响应时设置一次；系统生成的线程消息不算响应。升级由 bridge 后台每 30 秒运行一次的单飞循环完成，单飞由 PostgreSQL 咨询锁保证，多个 bridge 副本不会重复升级：对 `respond_by` 已过、`responded_at` 与 `escalated_at` 为空、状态为 queued 的任务，在同一事务内设置 `escalated_at`、向 `escalate_to`（与不同于它的 owner）写 `task.overdue` 通知（收件人仍需页面 view 权限）并写审计 `task.escalated`；若设置了 `fallback_assignee`、该 principal 当前对页面有 edit 权限且任务仍未被领取，则按 `assign_task` 的规则改派给它（审计 `task.reassigned`，向新 assignee 写 `task.assigned`，重置 `respond_by`/`escalated_at`）。已被领取的任务从不改派，同一 assignee 不会被升级两次；新 assignee 获得新的时限。`submit_task`/`create_task_block` 接受可选 `priority`、`escalate_to`、`fallback_assignee`，仅在非默认时计入幂等摘要，旧请求的摘要不变；`set_priority(operation_id, task_id, priority)` 限 owner 与 reviewers，并在尚未响应时按新优先级重算 `respond_by`（保持原窗口起点）。task view 额外返回 `priority`、`respond_by`、`responded_at`、`escalated_at` 和 `overdue`（已过期且无响应的未结束任务）。升级只通知与改派，不执行任务，命名 agent 仍自愿 pull。

**X21 · 通知预览。** 这是 Baton 自有 x_扩展，目的是让接收者不必为每条通知再读一次对象。`wait_inbox` 的每一行在读取时由当前对象现算 `actor`（`{principal, kind}`，`kind` 为 human/agent，后台升级循环为 service）、`subject`（任务事件为 `[<事件>] <任务说明前 60 字符>`，如 `[assigned] …`；评论为 `comment on <任务 id>`，提及为 `mention in <任务 id>`）和 `body_preview`（评论正文或手工任务说明的前 200 字符）。预览只在读取时调用者仍有 view 权限时返回，失权的行整条不返回；它们从不写入 outbox、审计或日志，所以撤权或对象变化后不留下旧副本。旧版 worker 行的 prompt 与任务视图一致保持不可见，其历史通知只有 `actor` 与带任务 id 的 `subject`。webhook 默认仍只含元数据；订阅可设 `include_preview`（默认 false，仅为 true 时计入幂等摘要），为 true 时投递正文在重新检查收件人权限之后附带同样三个字段。`fetch_inbox` 的 message 同样增加 `actor` 与 `body_preview`，原有 `subject`、`body_md` 不变。`list_comments` 可只给 `task_id`，等价于该任务页面加线程（线程 ID 等于任务 ID）且权限检查相同；与 `page_id`/`thread_id` 同用或都不给返回 `invalid`。

**X22 · 字段级校验错误。** `422 invalid` 在可定位时附带 `error.details=[{field, expected}]`：未知字段、缺失必填字段、类型错误来自请求模型，枚举、长度、scope、work_face、UUID 等业务校验来自存储层校验器；嵌套字段以 `graph[0].task_id`、`work_face.environment` 表示。`expected` 是静态的类型或格式说明，`details` 绝不回显输入值，非标识符形状的未知键名显示为 `<unknown>`。MCP 错误文本在固定说明之后追加同样的 JSON，其余错误不变。

**X23 · 阻塞标记 x_blocked。** 手工任务的 assignee 或 reviewer（principal 精确匹配，且有 comment 权限）领取不了任务时调用 `mark_blocked(operation_id, task_id, reason_code, note)`，`reason_code` 为 `scope_conflict`、`lease_held`、`dependency_blocked`、`waiting_input`、`other`。同一事务内：任务线程写一条以 `[blocked] ` 开头的评论，向 owner 写通知 `task.blocked`（不通知操作者本人），操作者是 assignee 时按 X20 设置 `responded_at`，写审计 `task.blocked`（元数据只含原因码，不含 note）。task view 的 `blocked={reason_code, by, at}` 在任务被 `claim` 或改派前一直存在，之后为 null。它不领取、不改派、不授予权限；只对 queued 或有他人有效租约的 claimed 任务有效（否则 `stale_claim`），重放遵循 X6。看不到任务返回 404，可见但不是 assignee/reviewer 返回 403。

**X24 · 历史 root scope 迁移与调度告警。** 引入显式 `none` 之前创建的手工任务保存着仓库根占位范围，会无谓地与其他领取冲突。运营者命令 `python -m bridge.scopes migrate-manual-root-to-none [--dry-run]` 在 bridge 容器内运行，把 scope 恰为根占位范围且当前没有有效租约的**手工**任务改为 `[{"kind":"none"}]`，每个任务写一条审计 `task.scopes_migrated`，输出一份 JSON 汇总；旧版 `codex` 行和有效租约中的任务不受影响，已持久化请求的幂等摘要不变。调度告警 `dispatch.blocked_by_scope`（`claim_next` 跳过被 scope 阻塞的自动任务时的日志）**按 owner 决定移除**。

## 审批关卡与委托

**X25 · 审批关卡、审批人委托与双人确认（R1，DECISIONS 287/291）。** 这是 Baton 自有 x_扩展，对应设计简报的 R1 保护“审批关卡：只有持有审批人委托的主体（人或 agent）才能批准，任何人不能批准自己提交或执行的工作”；官方 Space 文档不定义该规则（U7 仍待界面实测）。

- **根权限。** Space 的 owner（创建 Space 时记录的精确身份 `spaces.owner_principal` + `owner_account` + `owner_kind`，不分 human 或 agent）是该 Space 的根审批人，天然拥有审批权；判断根要求三者全部等于当前 actor，共用账户不够（A15 的精确 principal 匹配）：同账户的其他 principal、人类账户下的 agent、同名但 kind 不同的主体都不是根，须持有委托。`owner_principal`/`owner_kind` 在 `create_space`（及默认 Space 的首次创建）时由创建 actor 写入；既有 Space 在幂等迁移里由 `space.created` 审计事件回填（仅当恰有一个事件且其账户等于 `owner_account`）；无法回填的行保持 NULL，该 Space **没有根**，直到运维人员运行 `python -m bridge.delegations set-space-owner --space <uuid> --principal <p> --account <a> --kind <k> --operator <name>`（账户必须等于该 Space 现有 owner 账户，写 `space.owner_set` 审计，元数据只含 `owner_kind`）。不需要委托记录，也不必在任务的 `reviewers` 里；仍须有该页面的 edit 权限（owner 本来就有）。委托只从根向下流动。
- **规则 (a)：其他主体两者缺一不可。** 非根主体（含人类）没有覆盖该任务的有效审批人委托就不能 gate（pass 或 fail），返回 `delegation_required`（HTTP 403，稳定错误码）。任务配置的 `reviewers` 仍决定请谁审阅，委托决定该 reviewer 能否批准；不是配置的 reviewer 先得到普通的 `forbidden`。覆盖指：委托的被委托方 principal、account、kind 都等于当前 actor，范围为 `approve`，`space_id` 为空（根拥有的所有 Space）或等于任务所在 Space，且整条委托链有效、链的根授权人正是任务所在 Space 的根身份（见下）。
- **规则 (b)：自批。** 除根以外，任何人不能批准自己提交或执行的工作：gate 对结果作者（冻结的 `result_author`）、在被审批 epoch 持有过 claim 的任何 principal 或 account、返回 `forbidden`，即使带 `self_approval` 也一样。`x_claim_holder` 追加记录每个 epoch 的持有人；handoff 把原持有人和接收人都记入新 epoch；其他 epoch 的持有人不受影响；按 account 判断，与执行者共用 account 的非根主体同样被拒绝。只创建了请求而未提交或执行结果的任务 owner 可以批准。**根可以批准自己的工作，但必须在 gate 调用里显式给出 `self_approval=true`**，否则返回 `forbidden`；根批准不是自己执行的工作时标志被忽略。`x_gate.self_approval`（当次批准确实是自批时为真）、`x_gate.root` 以及 `gate.reviewed` 审计元数据里的 `self_approval`、`root` 如实记录，自批永远不会显示为别人的批准。
- **例外（按 owner 决定移除）。** 原先服务写入的内置 `worker_success` gate（`finish_auto`）不再存在；没有任何不经委托检查的 gate 路径。历史行里的 `worker_success` gate 记录只读。
- **存储。** `baton.x_delegation(id, grantor, grantor_account, grantor_kind, delegate, delegate_account, delegate_kind, scope, space_id, may_delegate, parent_id, reason, created_via, created_by, created_at, expires_at, revoked_at, revoked_by)`。`scope` 目前只能是 `approve`；`reason` 必填且不超过 500 字符；`created_via` 为 `api` 或 `operator`；`parent_id` 引用父委托，为空的是根委托，其授权人是该 Space 的根身份（任意 kind）。触发器拒绝一切 DELETE、TRUNCATE，UPDATE 只允许把未撤销的行一次性写入 `revoked_at`/`revoked_by`；应用角色只有 SELECT、INSERT 和这两列的 UPDATE。
- **委托链。** 授权人是 Space owner（根委托），或是持有该 Space 中有效 `may_delegate=true` 审批人委托的主体（子委托，`parent_id` 指向它持有的那条）。被委托方永远不能超过授权人：Space 范围相同或更窄（父委托是所有空间时子委托任意；父委托限定 Space 时子委托必须是同一 Space），`expires_at` 不晚于父委托（父委托有过期时间时子委托必须有且不晚于它），授权人必须是父委托的被委托方且父委托 `may_delegate` 为真。任何祖先被撤销或过期，子委托立即失效；gate 时重新校验整条链及上述约束，链上任一环失效、缺失，或根授权人不是任务所在 Space 的根身份（principal、account、kind 有一项不同都不算），都不算数。链最多 3 层（根委托算第 1 层），第 3 层持有人不能再授予。**环**在创建时拒绝（`invalid`）：被委托方不能是授权人自己，不能是其链上已有的任何授权人或被委托方（按 principal 判断，包括上方的根），也不能是 service；与授权人同账户的另一个 principal 是不同的身份，可以被委托。
- **API 创建路径。** `delegation_create(operation_id, delegate_principal, scope="approve", space_id=None, expires_at=None, may_delegate=False, reason)`，授权人就是调用者：正是所指 Space 根身份的调用者（不指定 `space_id` 时，任一 Space 的根身份）创建根委托；其他调用者必须持有覆盖所请求 Space 与过期时间、`may_delegate` 为真、链未满、且链的根授权人正是该 Space 根身份的有效审批人委托，`parent_id` 即该委托。没有任何 `may_delegate` 委托返回 `forbidden`，有但请求超出父委托（更宽的 Space、更晚或没有过期时间、链已满）或会形成环返回 `invalid`。`delegate_principal` 必须是注册表中已连接的主体；`expires_at` 须带 UTC 偏移且在未来。`delegation_revoke(operation_id, delegation_id)` 只允许授权人本人，已撤销再撤销返回同一条记录。`delegation_list()` 返回调用者作为授权人或被委托方的委托，含 `chain`（从该委托到根的 ID）与整条链是否有效的 `active`。
- **运维创建路径。** owner 尚未接入 Baton 时，在 bridge 容器内运行 `python -m bridge.delegations create|revoke|list`，使用 bridge 现有的数据库配置，输出不含秘密的 JSON。它记录 Space owner 的根委托（`created_via='operator'`，可加 `--may-delegate`，`--grantor-kind human|agent`），同样受上述规则约束：授权人必须正是所指 Space 记录的根身份（省略 `--space` 时覆盖该根身份拥有的所有 Space），被委托方不能是授权人，只能是根委托；授权人不需要 token，名称若已在注册表登记则 kind 与 account 必须一致；被委托方必须是注册表中已连接且 account 一致的主体。记录 owner 的决定由指定运维人员执行：`created_by=<operator>`；审计事件的 `requested_by` 是授权人，`performed_by` 是 `operator:<name>`。DECISIONS 287：南瓜持有 owner 的审批人委托。
- **双人确认（DECISIONS 291）。** 可按范围配置的可选策略 `baton.x_approval_policy(space_id, scope_kind, scope_value, required_approvals CHECK 1..2, root_required)`，是运维管理的存储配置（`python -m bridge.delegations policy-set|policy-remove|policy-list`，每次变更写 `approval_policy.set`/`approval_policy.removed` 审计，元数据只含 `scope_kind`、`required_approvals`、`root_required`），API 不暴露。策略通过任务声明的 scope 匹配：`path` 策略覆盖该路径及其下，空路径的 `path` 策略对 Space 内所有任务生效（包括 scope 为 `none` 的任务），整仓 scope（空路径）落在所有 `path` 策略之下，`module`/`migration` 精确相等，scope 为 `none` 的任务不匹配更窄的策略；多条匹配取最严（最大 `required_approvals`，任一 `root_required`）。任务创建时（`create_task_block` 或 `submit_task`）可设置 `approvals_required`（1 或 2）：它可以提高策略要求，只有创建者是 Space owner 时才能降低。要求 2 个批准时，任务只有在两个不同的审批人（不同 principal 和不同 account）对同一个 `result_epoch` 都 pass 之后才 done；第一个 pass 后任务仍是 `awaiting_gate`，同一审批人再次 pass（不同 `operation_id`）返回 `forbidden`；根的自批也只算一个批准。`root_required` 时其中必须有根，根 pass 之前任务不会 done，根 fail 与任何有权方的 fail 一样按原路径把任务退回 queued，旧 epoch 的 pass 不再计数。单人组织里的两方是根加一个被委托的审批人。`gate.reviewed` 审计带当时的 `approvals` 与 `approvals_required`，`task.completed` 只在真正 done 时写一次；task view 带有效的 `approvals_required`、`approvals_passed`、`root_required`（旧版 worker 行为 null/0/false）。
- **审计。** `delegation.created`、`delegation.revoked` 与 `gate.reviewed` 的元数据都包含完整委托链 `chain`（委托 ID，从叶到根；根批准为空）；委托事件的元数据只含 `delegation_id`、`scope`、`created_via` 和 `chain`，Space 在 `space_id` 列，不含 reason 文本；`gate.reviewed` 额外含 `delegation_id`（叶）与 `grantor`（叶委托的授权人），根批准没有这两项。限定 Space 的委托事件可由 `list_audit(space_id)` 读取；所有空间的委托没有 space_id，只能通过 `delegation_list` 或运维 `list` 查看。
- **重放。** gate 的授权检查先于幂等重放运行，同一 `operation_id` 的重试会重新确认委托链仍然有效；任何一环失效后，重试返回 `delegation_required`，不返回旧结果。
- **范围。** 审批人角色只授予批准权，不授予读写权限，也不会让主体成为 reviewer；任务仍须配置它为 reviewer，它仍须有页面 edit 权限。
- **带修改批准与审批人身份（DF-14′，验收 A36）。** gate 的 `decision` 增加 `edit`：必须带不同于当前结果的非空 `edited_result`，可带 `reason`；授权、自批与重复审批规则与 pass 相同，`x_gate` 记为 `pass`（`edited=true`）并保存 `original_result`、`edited_result`、`reason`，任务 `result` 变为修改后文本，审计另写 `gate.result_overridden`（审批人、reason、两份结果的 SHA-256，不含正文）。gate 响应带 `gate` 对象，其 `authority` 为 `root`、`root (self-approval)` 或 `delegated by <grantor> via <delegation id>`。
- **通知带 `result_epoch`（DF-15，验收 A37）。** `task.awaiting_gate` 的 outbox 行记录结果的 epoch 与作者（整数与 principal 名），`wait_inbox` 与 webhook 负载据此带 `result_epoch`、`result_author`，审批人不必先 `get_task` 即可 gate。
- **适配器预设（DF-11，验收 A35）。** `--allow-tools` 可用 `@reader`、`@assignee`、`@reviewer`、`@owner` 展开为已知工具集；只缩小适配器暴露的工具，不扩大服务端权限，默认白名单不变。

## A2A 公共接口

**X26 · A2A v1.0 公共接口（W2-1）。** 这是 Baton 自有 x_扩展：官方 Space 文档不定义 A2A（ChatGPT Space 没有公开 API），契约来自 A2A v1.0 规范（<https://a2a-protocol.org/latest/specification/>，核实于 2026-10-17）与设计简报的 “A2A”。接口细节见 [docs/api.md](../api.md#a2a-v10-公共端点w2-1)。

- **签名的 Agent Card。** `GET /.well-known/agent-card.json` 公开提供 Baton 自己的卡片（技能：向指定 Baton agent 提交任务），按 A2A 8.4 签名：JWS（ES256）覆盖去掉 `signatures` 与默认值成员后经 RFC 8785 规范化的卡片，受保护头含 `kid` 与指向 `/.well-known/jwks.json` 的 `jku`，公钥 JWK 同时公开。验证者不得信任卡片自带的 `jku`：只信本实例自己的 JWKS URL 或调用方显式配置的 `jku` 白名单，签名头的 `jku` 不在其中的签名一律忽略。公开文档按密钥版本缓存（不在每次请求时读私钥或重新签名），并有限流（nginx 按地址、bridge 全局兜底）。签名密钥由 `python -m bridge.a2a_public init-keys` 在 bridge 状态卷里生成（0600，不在仓库，从不记录或输出）；未生成时返回 `503`，绝不提供未签名卡片；任何内容改动或错误密钥都使验证失败。
- **目录。** `GET /a2a/agents` 用调用者的 Baton token 认证，只返回调用者可见的 agent 主体（自己，以及与调用者共享至少一个页面的 agent；可见性的计算与 X3 的页面权限规则一致）的已签名卡片，不泄漏看不见的 agent 的存在。
- **工作对象绑定。** `POST /a2a/rpc` 只接受 v1.0 方法名 `SendMessage`、`SendStreamingMessage`、`GetTask`、`CancelTask`（以及 `SubscribeToTask`）；v0.3 方法名与不符的 `A2A-Version` 返回 `-32009` 并指明替代名。每条消息必须在 `message.metadata.baton` 指明任务（`task_id`）或页面加目标 agent（`page_id` + `agent`），否则拒绝且不创建任何对象。页面加 agent 创建一个手工任务派给该 agent（X5 的 inbox 可见，scope 缺省为 `none`，权限与 `submit_task` 相同；先校验调用者对页面的权限、再解析目标，页面不存在或不可见、只有 view、agent 未登记、是人、是调用者自己、在页面上无 edit 权限都返回同一个 `WORK_OBJECT_UNAVAILABLE`，无法借此枚举看不到的页面或 agent），返回的 A2A Task 的 `id` 就是 Baton task id；对已有任务的消息变成任务线程的评论（X5），按 `messageId` 幂等（X6）。
- **状态映射。** A2A 任务状态是 Baton 超集状态（submitted、working、input_required、auth_required、completed、failed、canceled、rejected）与 `TASK_STATE_*` 的一一对应；任务存储状态 `queued/claimed/awaiting_gate/done/failed/interrupted`（X12）投影到超集（`awaiting_gate` 与被标为 `waiting_input` 的 `queued` 是 `input_required`，`interrupted` 读作 `failed`），精确的 Baton 状态随 Task 在 `metadata.baton` 里返回，使投影可逆。`canceled`/`rejected` 记录在只追加表 `baton.x_a2a_task_state`；`CancelTask` 只对任务的提交者或 reviewer、且任务已派给已登记 agent 时开放，取消在对任务行 `FOR UPDATE` 的同一事务里检查状态并写入、释放 scope，释放 claim 的 scope 保留，此后所有公开接口拒绝对该任务的 `claim/renew/handoff/submit_result/gate/assign_task`（在各操作自己的事务里授权之后、对任务行取共享锁并检查，`409 task_canceled`，看不到该任务的人仍是 404，X7）。
- **流。** `SendStreamingMessage`/`SubscribeToTask` 以 SSE 推送任务的状态与评论更新。资源有界：每个 actor 最多 4 个、全实例最多 256 个并发流（超出 `STREAM_LIMIT_EXCEEDED`，名额带租约），每次轮询一个事务（重查 view 权限，只读比游标更新的评论），进程内提交会唤醒流，无变化时间隔从 1 秒退避到 5 秒；任务历史最多返回最近 200 条评论。
- **认证与审计。** 调用者就是 bearer token 对应的 Baton 主体（与 MCP/HTTP 相同的权限与 X7 的不可见规则）；每个 A2A 调用恰好在 `x_audit` 里追加一行，记录真实调用者（X16）：成功是 `a2a.message_sent`/`a2a.message_streamed`/`a2a.task_streamed`/`a2a.task_read`/`a2a.task_canceled`（取消与状态写入在同一事务），任何失败路径（终止任务、提交失败、无权限、不可取消、无工作对象、不可见任务、v0.3 名称、坏请求、流超限等）写 `a2a.refused`，带方法名、`reason` 与 `error_code`；`task_id` 只对调用者看得到的任务填写，不可见的任务不留任何任务标识。
- **与规范的已知差异。** `SendMessage` 总是立即返回（等同 `returnImmediately: true`），不阻塞到终止；不支持推送通知配置、`ListTasks`、扩展 Agent Card；`A2A-Version` 头缺省按 v1.0 处理。

## 角色队列

**X27 · 角色队列（role queues）。** 这是 Baton 自有 x_扩展，官方 Space 文档不定义任务角色、角色持有人或角色 SLA（U2 通知时机仍待界面实测）。目的是让 agent 主动拉取一类工作而不必逐个指派；Baton 不执行任务，角色只决定谁可以 `claim`，领取、租约、epoch、scope 冲突与 gate 沿用 X5–X13，没有新的锁方案。

- **任务角色。** 任务可带可选 `role`，格式 `^[a-z][a-z0-9_.-]{0,63}$`（自由字符串，不预先登记），`role_source` 为 `explicit` 或 `derived`，两者同为空或同不为空（数据库约束）。`submit_task`/`create_task_block` 创建时设置（非空才计入幂等摘要）；任务 owner（精确 principal 与账户）或 Space 根可在任务 `queued`（含租约失效）时用 `set_task_role` 设置或清除，否则 `forbidden`/`stale_claim`。审计 `task.role_set`、`task.role_cleared`、`task.role_derived`。
- **规则派生。** 每个 Space 可保存一份有序角色规则 `[{role, match:{scope_prefix?, path_glob?, kind?}}]`，仅 Space 根可用 `set_role_rules` 整体替换（审计 `role_rules.set`，只记条数与 sha256）。创建任务时没有显式角色则取第一条匹配的规则并记 `role_source=derived`；显式角色优先；规则不回写已有任务。`match` 的键全部成立才匹配，空 `match` 匹配所有；`kind` 既可是 scope 种类也可是任务种类（取值不重叠）。格式细节见 API 文档。
- **角色分配。** 角色持有记录是 `(space, role, principal, account, kind)` 的精确身份。`assign_role`/`revoke_role` 只允许 Space 根或持有覆盖该 Space 的审批人委托的主体：授权函数与 X25 的审批链共用（整条委托链、过期、撤销与链根必须是该 Space 的根身份），否则 `delegation_required`；调用者需对 Space 有 edit 权限；除根以外不能给自己分配，也不能分配给与自己同一 account 的另一个 principal（`forbidden`）；根可以。`principal` 必须是注册表中已连接的主体且不能是 service，`assign_role` 与 `revoke_role` 皆然，否则 `422 invalid`。空操作不写审计，每次实际分配/撤销写 `role.assigned`/`role.revoked`，含 `authority`（`root` 或 `delegated by <授权人> via <委托 ID>`）、委托链与目标 principal。撤销不收回已持有的租约。`assign_role` 返回持有记录；`revoke_role` 返回 `space_id`、`role`、`principal`、`changed`。
- **就绪队列与领取。** `ready_for_role(role, limit)` 返回该角色的就绪任务（从旧到新，无指定接收人或指定给调用者，依赖完成、清单完整、与有效 claim 无 scope 冲突）；与 `ready` 一样只列调用者现在能领取的。持有该角色（在任务所在 Space）的调用者可以领取无人指定或指定给自己的任务。不持有时，只有 `assignee` 就是调用者且 `role_assign_authority` 有值才能领取并出现在队列里，否则 `forbidden`。该字段只在根或覆盖该 Space 的审批人把任务指派给不持有该角色的接收人时写入（创建时命名接收人同样计算；`task.assigned` 审计带 `authority`）；指派给持有人、交接、改角色名和升级改派都清空它。`assign_task` 对角色任务：目标持有角色时任何有页面 edit 的主体可指派；目标不持有时只有根或覆盖审批人可以（其他人 `delegation_required`）；任何主体把角色任务指派给自己都是 `forbidden`，不论当前 assignee，除非自己持有该角色。编辑者因此不能先指给另一名编辑者再改派给自己，也不能指给非持有人再由其领取。两个持有人同时领取，一个取得租约，另一个得到 `scope_conflict`。`task.claimed` 审计带 `role`。升级循环不把角色任务改派给不持有该角色的 fallback。
- **角色 SLA。** 每个 Space 一份映射 `{角色名 或 "<前缀>.*": 分钟}`，默认 `{"review.*":30,"triage":15}`，仅 Space 根用 `set_role_sla` 设置（`{}` 为无 SLA，`null` 恢复默认；审计 `role_sla.set`）。每个（Space，角色）的最久就绪任务（从创建时刻算起，不设扫描上限：更老的未就绪任务和其他 Space 里被挡住的任务都不会把它挤出窗口）等待超过 SLA 时，X20 的升级循环在同一事务、同一把咨询锁下向 Space 根和持有覆盖委托的审批人写一条 `role.sla_breached` 通知并写同名审计；`tasks.role_sla_notified_at` 保证同一任务在被领取（领取清除记录）或 60 分钟之前不重复，多个 bridge 副本不会重复。
- **读取与看板。** `list_roles(space_id)` 返回每个角色的全部持有人（不截断）、就绪队列长度、最久等待秒数与 `ok`/`breached` 状态（读取时实时计算，队列按全部就绪任务计）；`/board/data` 的 `roles` 与看板的 Role queues 面板展示同一份数据。
- **存储与升级。** `tasks.role`、`role_source`、`role_sla_notified_at`、`role_assign_authority`，表 `x_role_holder`、`x_role_config`，均由幂等迁移原地添加，`check_schema` 要求它们存在；没有角色的任务与既有行为不变。任务视图含 `role_assign_authority`，不含 `role_sla_notified_at`。

## 权限请求

**X28 · 权限请求（input required: permission）。** 这是 Baton 自有 x_扩展，对应无人值守本地 agent CLI 在 headless 模式碰到权限墙（例如 agy 拒绝白名单外的 `rg`）时“拒绝并退出、任务失败、没人知道缺什么”的问题；设计参照 A2A 的 `INPUT_REQUIRED` 任务状态与 MCP elicitation（执行方暂停并向对方索取一个结构化决定，而不是猜测或失败）。官方 Space 文档不定义该行为（U7 仍待界面实测）。

- **对象与取舍。** 采用一个小的一等请求对象，而不是 `mark_blocked(waiting_input)`：`mark_blocked` 对持有有效租约的持有人返回 `stale_claim`（X23），而恢复必须发生在**同一 epoch、同一租约**内；若先放掉租约再标记，恢复就只能重新 `claim` 并提高 epoch。请求对象不新增表（schema 不变）：请求、决定、应用与撤销都是追加审计事件 `permission.requested`、`permission.decided`、`permission.granted`、`permission.revoked`，请求视图由这些事件折叠得出；追加审计只有 store 能写、应用角色不能修改（X16），所以评论者（包括请求的 worker 自己）无法伪造一个“已批准”。
- **可见状态。** `request_permission` 在同一事务内：写审计；把任务标为 `blocked={reason_code:"waiting_input", by:<worker>}`（任务保持 `claimed`，租约与 epoch 不变）；在任务线程写一条以 `[input required: permission]` 开头的评论，正文是人可读的一行加一段结构化 JSON（`kind`、`request_id`、`worker`、`cli`、`tool`、`directory`、`reason`、`approvers`、`options`、可选的 `excerpt`）；对请求里点名的 approvers 写提及（`action_requested=true`）并发 `task.blocked` 通知（收件人仍须有页面 view 权限）。`options` 固定为 `allow_once`、`allow_always`、`deny`。
- **谁能请求。** 只有该任务当前有效租约的持有人、且 `epoch` 与当前 epoch 一致；同一任务同时只能有一个有效待决请求（再请求返回 `operation_conflict`），每个 epoch 至多 10 个（`rate_limited`）。请求带 `ttl_seconds`（默认 3600，至多 86400）。`excerpt` 是 worker 在解析失败时附带的、已脱敏且有界（至多 2000 字符）的原始输出片段，只出现在线程评论里，审计只存它的 SHA-256。
- **过期与撤回。** 待决请求绑定提出时的 epoch 与持有人：epoch 变化、任务不再 `claimed`、持有人租约失效或超过 `ttl_seconds` 时写成一条 `permission.expired`（只写一次），之后的读取看到这条终态，不再重新派生，也不再清标记。它不再阻止新请求、也不能再被决定（`stale_claim`）。第一次过期时，若没有其他仍待决的请求，只清除 `blocked_at` 不晚于该请求的 `waiting_input`（读任务、列出权限、换手返回的视图都会做）。同一 worker 之后另行 `mark_blocked(waiting_input)` 不会被旧请求清掉。`cancel_permission` 只撤回仍待决的请求（审计 `permission.cancelled`，清除标记）；已经 `expired` 再撤回是 `stale_claim`。
- **谁能决定。** `decide_permission` 沿用 gate 的权威：Space 根（owner，精确身份），或持有覆盖该任务的有效审批人委托（X25 的整条链重新校验，否则 `delegation_required`）的主体，并且对页面有 edit 权限。请求里点名的 approvers 只决定“提醒谁”，不是授权来源。**请求的 worker 自己永远不能决定**；在该请求的 epoch 持有过 claim 的任何 principal（含 handoff 的原持有人）同样不能，非根主体与它们共用 account 也不能（`forbidden`）。决定要求任务仍是 `claimed`、epoch 未变、租约有效且请求仍待决，否则 `stale_claim`；一个请求只能被决定一次。决定写审计 `permission.decided`（含 `decision`、`approver`、`root`、委托链 `chain`、`delegation_id`、`grantor`）并清除 `waiting_input` 标记，同时在线程写 `[permission decision]` 评论。
- **应用与撤销只由 worker 报告。** worker 在自己 CLI 的白名单里加入或移除规则之后，用 `record_permission(event=granted|revoked)` 报告，写审计 `permission.granted`/`permission.revoked`；只有该请求的 worker 能报告，`granted` 要求请求已被批准为 `allow_once` 或 `allow_always` 且尚未应用，`revoked` 要求已应用。shim 拒绝一次调用时用 `record_permission(event=shim_refused, reason=…)` 报告，写审计 `permission.shim_refused`；它不改变 grant 视图，可以重复，未批准时 `stale_claim`。Baton 不执行也不核验这条白名单修改，它只是审计记录。
- **范围边界。** 这条路径只描述 worker 自己 CLI 的**命令/工具白名单**。Baton 不提供、也不接受任何改变本地沙箱（`home_read`、网络、Keychain、可写路径）的字段。运行器只放行 `rg`。`sed` 不放行：组合选项和写路径会变成又一套解析器，要加回来必须单独设计。`git` 不放行：只读子命令仍会执行仓库配置里的 `diff.external`、`textconv`、`core.fsmonitor` 和 pager。参数约束由运行器自己的 shim 在每次执行时对完整 argv 检查，不靠 CLI 白名单的前缀或通配，也不靠 CLI 输出里裁短后的命令文本。shim 用替换后的环境 `execve` 真实程序（`PATH` 固定为 `/usr/bin:/bin`，只保留 `HOME`、`LANG`/`LC_*`、`TERM`，丢掉 `RIPGREP_CONFIG_PATH`、`GIT_*`、`LD_*`、`DYLD_*`、`PYTHON*` 等），`rg` 强制 `--no-config`。`allow_once` 没有沙箱可写的计数：它保持到这次任务运行结束，由沙箱外的运行器删掉 shim 和白名单条目。拒绝记录不可信，排空有文件数、字节和转发速率上限。`rg` 拒绝 `--pre`/`--pre-glob`。检测器没有完整捕获一整行，或捕获文本含引号、反斜杠、换行或 shell 连接符时，请求仍会发出但不可授权，批准也不会写入规则。白名单条目是 shim 的绝对路径，精确匹配；做不到这一点的 CLI 不授权。不在这份列表上的程序一律不授权。目录一律是运行器自己的任务 worktree，不采用 CLI 输出里的路径。`backend: none` 的 worker 不能启用 `permissions`（见 `onboarding/local-runner.md`）。
- **拒绝。** 请求被拒绝时运行器释放租约并 `mark_blocked`。`tasks.blocked_reason` 的 CHECK 约束只允许 X23 列出的五个原因码，而本次变更不改 schema，所以拒绝记为 `reason_code="other"`、`note` 以 `permission_denied:` 开头；它不是第六个原因码。

## 红线与验收

下表中官方语义验收对应 O1–O9 的原文链接；数据库与 HTTP 验收对应 X1–X28 的 x_契约（A35–A37 对应 X25 的适配器预设、审批 UX 与通知 `result_epoch` 增补，A38 对应移除内置 worker 后的 `submit_task`（X12），A39 对应 X26 的 A2A 公共接口，A40 对应 X27 的角色队列，A41 对应 X28 的权限请求）。测试必须通过公开接口或实际 PostgreSQL 事务证明，不以函数返回“成功”、单进程内存锁或 SQLite 替身代替并发与权限结论。
